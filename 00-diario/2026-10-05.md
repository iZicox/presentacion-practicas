# 2026/10/03

- explicacion de la ia de como hacer la integracion con el erp

Tu arquitectura es sensata y la base de datos no queda expuesta. El punto que más cuidado pide es el control de quién ve el stock, porque ahí fallan más a menudo las integraciones con WordPress.

Flujo recomendado: navegador → WordPress (comprueba el login) → Worker de Cloudflare → túnel → API del ERP. El navegador del cliente no debe hablar nunca con el Worker.

## Valoración de la idea

Cloudflare tiene una función para esto: [Workers VPC](https://developers.cloudflare.com/workers-vpc/) conecta un Worker a APIs privadas a través de Cloudflare Tunnel, sin exponer puertos a Internet público. Registras el servicio del ERP como "VPC Service" (host, puerto y túnel) y el Worker lo llama con `env.PRIVATE_API.fetch(...)`. Es una función reciente, así que verifica que tu plan la incluya. [developers.cloudflare](https://developers.cloudflare.com/workers-vpc/)

El Worker solo puede acceder a ese servicio concreto, no a toda la red, lo que reduce el daño si algo falla. Otra consecuencia es que `cloudflared` debe correr en un equipo que alcance al ERP. Si ese equipo cae, el Worker pierde acceso aunque esté sano. Conviene prever un mensaje de respaldo en la web, por ejemplo "Consultar disponibilidad". [blog.cloudflare](https://blog.cloudflare.com/workers-vpc-open-beta/)

## Autenticación en cada tramo

**WordPress → Worker.** Hay dos opciones.
- **Cloudflare Access con service token (la que prefiero).** Pones Access delante del dominio del Worker, por ejemplo `stock.tudominio.com`. Access genera un Client ID y un Client Secret, y el PHP los envía en las cabeceras `CF-Access-Client-Id` y `CF-Access-Client-Secret`. Cloudflare los valida antes de que la petición llegue a tu código. Los tokens caducan al año y hay que rotarlos. [developers.cloudflare](https://developers.cloudflare.com/cloudflare-one/access-controls/service-credentials/service-tokens/)
- **Clave propia o HMAC.** El Worker valida una cabecera `X-API-Key`, o mejor una firma HMAC-SHA256 de `método + ruta + timestamp`, y rechaza si el timestamp tiene más de 60 s. Es más trabajo, pero no depende de Access.

En ambos casos, guarda el secreto en `wp-config.php` (`define('STOCK_API_SECRET', ...)`) y no en la base de datos ni en el tema. En el Worker, usa `wrangler secret put`.

**Worker → ERP.** Aunque el túnel ya aísla la red, pide también una API key propia del ERP, que el Worker guarda como secreto. Así hay una segunda barrera si alguien llegara al túnel.

## Login del cliente en WordPress

Hay que impedir que se vea el stock sin sesión, y que la caché lo enseñe a quien no debe.

1. Comprueba `is_user_logged_in()` dentro del shortcode, en PHP del servidor. Si no hay sesión, no llames a la API y muestra "Inicia sesión para ver el stock".
2. No pongas JavaScript en el navegador que llame al Worker. Cualquiera vería el token en las herramientas de desarrollo.
3. Si usas caché de página completa (WP Rocket, LiteSpeed, APO de Cloudflare), el HTML con el stock puede servirse a visitantes anónimos. Hay dos soluciones:
   - Excluir de la caché a los usuarios logueados y a esas páginas.
   - Mejor: que el shortcode pinte un contenedor vacío y un pequeño JS pida el dato a un endpoint propio de WordPress (`register_rest_route`) con `permission_callback => is_user_logged_in`. Ese endpoint es el que llama al Worker. Así la página se puede cachear y el dato sigue protegido.
4. Si quieres limitarlo a clientes aprobados y no a cualquier registrado, comprueba un rol (`current_user_can('cliente_b2b')`).

Un esquema del shortcode:

```php
add_shortcode('stock_erp', function($atts){
  if (!is_user_logged_in()) return 'Inicia sesión para ver el stock.';
  $sku = sanitize_text_field($atts['id'] ?? '');
  $key = 'stock_'.md5($sku);
  $val = get_transient($key);
  if ($val === false) {
    $r = wp_remote_get('https://stock.tudominio.com/producto/'.rawurlencode($sku), [
      'timeout'=>5,
      'headers'=>[
        'CF-Access-Client-Id'=>STOCK_CF_ID,
        'CF-Access-Client-Secret'=>STOCK_CF_SECRET,
      ],
    ]);
    if (is_wp_error($r) || wp_remote_retrieve_response_code($r)!==200) return 'Consultar disponibilidad';
    $val = json_decode(wp_remote_retrieve_body($r), true)['stock'] ?? null;
    set_transient($key, $val, 60);
  }
  return esc_html($val);
});
```

La caché con transient funciona bien aquí porque el stock es igual para todos los clientes. Si algún día muestras datos distintos por cliente, como precios o stock reservado, la clave debe incluir el ID de usuario. El Worker también puede cachear 30–60 s para no saturar el ERP. [wpskills101](https://wpskills101.com/wordpress-transients-api-caching-data-the-right-way-in-code/)

## Qué pedir al equipo del ERP

- **Endpoint de solo lectura:** `GET /producto/:id`, con respuesta `{"id":"ABC123","stock":42}`.
- **Identificador:** confirmar que `:id` coincide con el SKU que usa WooCommerce, o acordar la correspondencia. Si no, tendrás que mantener una tabla de equivalencias.
- **Errores:** 404 si el producto no existe, 401 si falla la clave, 429 si se supera el límite de peticiones. Todos en JSON.
- **Endpoint por lotes** (opcional, muy recomendable): `GET /productos?ids=A,B,C`, para listados y categorías sin hacer 50 llamadas.
- **Seguridad:**
  - HTTPS aunque sea interno.
  - API key obligatoria en cabecera.
  - Credenciales de ERP con permisos solo de lectura sobre la tabla o vista de stock.
  - Sin acceso directo a la base de datos.
  - Validar `:id` contra una lista o patrón permitido, para evitar inyección SQL.
- **Red:** la API escucha solo en una IP privada o `localhost`. Ningún puerto se abre en el router ni el firewall. `cloudflared` solo hace conexiones salientes.
- **Rendimiento:** respuesta en menos de 1–2 s y un límite de peticiones razonable.
- **Stock a publicar:** definir si es stock físico, disponible (menos reservas) o por almacén. Para B2B puede convenir enviar solo un rango o un semáforo, y no la cifra exacta.
- **Entornos:** una instancia de pruebas aparte para desarrollar sin tocar producción.

## Protecciones extra en Cloudflare

Añade una regla de rate limiting y una regla WAF al hostname del Worker (por ejemplo, solo aceptar la IP de tu hosting). Con Access delante, las peticiones sin credenciales ya no llegan al Worker. También conviene que el Worker valide el formato del `id` antes de reenviarlo al ERP.

Una pregunta para decidir el diseño: ¿tu WordPress usa WooCommerce con caché de página completa? De eso depende si basta el shortcode con comprobación de login o si te conviene el endpoint REST con carga diferida.
